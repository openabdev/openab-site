How we tested ui_action in OpenAB Computer 0.10.0

2026-11-10 · OpenAB Computer 0.10.0

Once an agent can read a window's accessibility tree, how does it press a button in that window without taking over your mouse? And after it presses, how do you prove it never touched the mouse?

OpenAB Computer 0.10.0 adds ui_action. The ui_snapshot tool from the previous dev note reads a window; ui_action acts on it. It takes a ref from a snapshot and presses a button or fills a field through the accessibility API, and the cursor stays where it is. This note covers what it does and how we tested it.

What ui_action does

The call is ui_action {snapshot_id, ref, action} (PR #96). The actions are press, set_value, focus, show_menu, confirm and cancel, plus increment and decrement. Each one maps to an accessibility action: press is AXPress on the element, set_value sets its AXValue and replaces the whole value. If the element does not support the action, the tool refuses before doing anything and lists the actions it does support.

The intended loop has three steps: ui_snapshot, then ui_action on one of its refs, then another ui_snapshot to check the result.

The tool never synthesizes input events and never moves the pointer; a test scans the source to keep it that way. By default it does not bring the app to the front or raise a window either. When that is needed, for example to open a menu in a background app, the caller passes activate: true.

A ref is only good in its own snapshot

The tool keeps the last four snapshots, for five minutes each. Before acting it checks the ref again: same process, same role and subrole, still under the window it was found in. For a menu item, the menu bar must still answer. If any check fails, the answer is stale ref: … take a new ui_snapshot. The tool never picks a lookalike element to stand in for the old one.

Who can use it, and password fields

ui_action is available only to the owner profile, in the same class as mouse and key, and it needs the macOS Accessibility permission. When it sets a password field, the value is never read back, logged or returned. For every field, the input value stays out of errors, log lines and response text. Through a switchboard, set_value on a password field is refused by default, unless the operator of that computer turns it on.

How we tested it

1. Unit tests with a fake accessibility provider

CI machines have no GUI, so the tests do not touch real apps. ui_snapshot already had a fake accessibility provider, and the ui_action tests run on it too. PR #96 added 52 tests in three suites: UIActionToolTests (40), UISnapshotCacheTests (5) and UIActivateTests (7).

They cover: a snapshot that expired or was pushed out; an unknown ref; an element that vanished, changed role, belongs to another process or left its window; an unsupported action, with the list of supported ones; which accessibility call sits behind each action; a password value absent from the response and from every log line; password fields refused by default through a switchboard; activate false by default; and the profile rules.

On an M4 Mac mini, swift test ran 256 tests with 0 failures, and every CI check on the PR passed.

We also tried a live run before merging, but that test build had no Accessibility permission, so ui_action only returned the permission error and the TextEdit run did not happen. It waited for the released build, which has the permission.

2. A live run on an M4 Mac mini, through the switchboard

After 0.10.0 was released, a remote agent drove an M4 Mac mini through the switchboard. Each step was one MCP tool call, and the switchboard's audit log recorded the times:

  1. Read the mouse location (a short JXA script through osascript, reading NSEvent.mouseLocation).
  2. Open TextEdit with a new document.
  3. ui_snapshot of TextEdit, 96 ms. The text area is [e3] AXTextArea.
  4. ui_action focus on e3 (8 ms), then set_value with "hello from ui_action 0.10.0" (15 ms).
  5. Another snapshot to check: e3's value is "hello from ui_action 0.10.0".
  6. Read the mouse location again.

Both readings gave the same point, (284, 88). The text went in and the cursor did not move.

3. What the live run caught: buttons inside a sheet

Next we quit TextEdit. The unsaved document brought up a save sheet, the kind of dialog that slides down from a window's title bar. ui_action press on the sheet's Delete button failed:

stale ref: e63 has left its window; take a new ui_snapshot and use its refs

It failed the same way three times, with a fresh snapshot each time. A read-only Swift probe showed why. Asked for its AXWindow, a control inside a sheet returns nil, not some other window. The 0.10.0 check treated "no AXWindow" as something only menu items do, so it refused the ref. The button's AXParent is the sheet, and it is the sheet whose AXWindow is the window.

This became issue #98 (labels bug and p2), fixed by PR #99. When an element has no AXWindow, or one that is not on the snapshot's recorded path, the check walks up AXParent to the nearest window, sheet, drawer or popover, and accepts the ref only if that container is on the recorded path. The walk stops after 50 steps, checks for cycles and runs under the same time budget. A change of process or role is still refused first, and no replacement is guessed.

PR #99 added 8 tests, for 264 in total with 0 failures, and CI passed. Its live check was read-only: applied to TextEdit's real save sheet, the new rule accepted all 15 controls in the sheet, Delete included; the 0.10.0 rule accepted none of them. The fix is merged and ships in 0.10.1. Pressing a button inside a sheet is covered by the unit tests; we have not yet re-run that press live through ui_action.

4. Two reviewers, and a leak in the audit log

Every change goes to two independent AI reviewers running different models. They review in parallel, and the change merges only when both approve the same commit. PR #96 went through five rounds and a confirming review.

The first round found a real problem. Through a switchboard, a password value sent with set_value ended up in the switchboard's audit log. The switchboard (openab-sb) writes each tool call's arguments to audit.jsonl before it forwards the call. So even when the Mac refused the call, the log line was already written. Only openab-sb could fix that, so PR #96 waited until the fix was merged and deployed.

The fix is openab-sb 0.2.2 (PR #16, issue #14). It redacts secret-bearing arguments in the audit line, at any depth in objects and arrays: the value of ui_action, typed text, keys whose names contain words such as password, secret, token or credential, and every value in env and headers. A string becomes <redacted:N chars>; any other type becomes <redacted>. Only the audit copy is redacted, and the computer still receives the real arguments. Free-form strings, such as a shell command, a script or a URL's query string, are not inspected.

We checked it with a canary. Through the deployed switchboard we sent one exec call with a fake token in its env, as API_TOKEN. In the audit file the canary appeared 0 times, and the line for that call held <redacted:31 chars> where the token had been. The live TextEdit set_value was logged as "value":"<redacted:27 chars>" too, and 27 is the length of "hello from ui_action 0.10.0".

The 0.10.0 release notes also ask switchboard operators to upgrade to openab-sb 0.2.2 before sending anything sensitive through ui_action, and to consider rotating audit files written by older versions.

Limits and next

  • set_value replaces the whole value. Some apps only commit it on confirm or when focus moves.
  • A press that opens a sheet or a menu may get a late answer from the app. The result is then reported as unconfirmed: it may have happened, so take a new snapshot instead of pressing again.
  • Drags and multi-step gestures stay on mouse. Custom-drawn content with no accessibility node stays on screenshot and mouse.
  • Linux: issue #67 is closed, because the macOS part is done. AT-SPI support for ui_snapshot and ui_action on Linux is deferred as p3 in issue #102, to be picked up when a Linux machine needs it. Until then, use screenshot, mouse and key on Linux.

To try it, update to OpenAB Computer 0.10.0, give it the Accessibility permission, and from an agent with the owner profile call ui_snapshot, then ui_action, then ui_snapshot again. If you use a switchboard, upgrade it to openab-sb 0.2.2 first. Previous note: OpenAB Computer can now read the macOS accessibility tree.
