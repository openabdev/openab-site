我們怎麼測試 OpenAB Computer 0.10.0 的 ui_action

2026-11-10 · OpenAB Computer 0.10.0

Agent 讀得到一個視窗的 accessibility tree 之後，要怎麼在不搶走你滑鼠的情況下，按下視窗裡的按鈕？按完之後，又要怎麼證明它真的沒碰到滑鼠？

OpenAB Computer 0.10.0 新增了 ui_action。上一篇開發筆記介紹的 ui_snapshot 負責讀畫面，ui_action 負責動手：拿快照裡的 ref，透過 accessibility API 按按鈕、填欄位，游標留在原地。這篇記錄它做了什麼，以及我們怎麼測它。

ui_action 做什麼

呼叫方式是 ui_action {snapshot_id, ref, action}（PR #96）。動作有 press、set_value、focus、show_menu、confirm、cancel，以及 increment、decrement，每個動作都對應一個 accessibility 動作：press 是對元素執行 AXPress，set_value 是設定它的 AXValue，整個值換掉。元素不支援這個動作時，工具在動手之前就拒絕，並列出它支援哪些動作。

建議的用法分三步：先 ui_snapshot，再對其中一個 ref 呼叫 ui_action，最後再拍一次 ui_snapshot 確認結果。

它從不合成輸入事件，也從不移動游標，原始碼裡有一個掃描測試盯著這一點。預設也不會把 app 叫到前景、不會拉起視窗。真的需要時，例如要打開背景 app 的選單，呼叫端要明確傳 activate: true。

ref 只在自己的快照裡有效

工具會保留最近四次快照，每次五分鐘。動手之前，它會重新檢查這個 ref：還是同一個行程、角色和子角色沒變、還在當初找到它的那個視窗底下；如果是選單項目，選單列要還在回應。任何一項不符，就回傳 stale ref: … take a new ui_snapshot。工具不會挑一個長得像的元素來頂替。

誰能用，以及密碼欄位

ui_action 只開放給 owner profile，和 mouse、key 同一級，也需要 macOS 的「輔助使用」權限。對密碼欄位 set_value 時，值不會被讀回、不會寫進紀錄，也不會出現在回應裡。對任何欄位，輸入的值都不會出現在錯誤訊息、紀錄或回應文字中。透過 switchboard 呼叫時，對密碼欄位 set_value 預設會被拒絕，除非那台電腦的管理者自己開啟。

我們怎麼測

1. 單元測試：用假的 accessibility 提供者

CI 機器沒有圖形介面，所以測試不碰真的 app。ui_snapshot 原本就有一個假的 accessibility 提供者，ui_action 的測試也跑在它上面。PR #96 新增三組共 52 個測試：UIActionToolTests 40 個、UISnapshotCacheTests 5 個、UIActivateTests 7 個。

涵蓋的情況有：快照過期或被擠掉；ref 不存在；元素消失、角色改變、屬於別的行程，或離開了原本的視窗；不支援的動作，要列出支援的動作；每個動作背後呼叫的是哪個 accessibility 動作；密碼的值不出現在回應和任何一行紀錄裡；透過 switchboard 時密碼欄位預設拒絕；activate 預設是 false；以及 profile 的權限劃分。

在一台 M4 Mac mini 上，swift test 跑了 256 個測試，0 個失敗；PR 上的 CI 檢查全部通過。

合併之前我們也試過實機測試，但那個測試版程式沒有「輔助使用」權限，ui_action 只回了沒有權限的錯誤，TextEdit 那段沒跑成。這段留到發布後，用已經授權的版本來做。

2. 實機測試：一台 M4 Mac mini，經過 switchboard

0.10.0 發布之後，我們讓遠端的 agent 經過 switchboard 操作一台 M4 Mac mini。每一步都是一次 MCP 工具呼叫，switchboard 的稽核紀錄記下了時間：

  1. 讀一次滑鼠位置（透過 osascript 跑一小段 JXA，讀 NSEvent.mouseLocation）。
  2. 打開 TextEdit，開一份新文件。
  3. 對 TextEdit 拍 ui_snapshot，花了 96 ms。文字區是 [e3] AXTextArea。
  4. 用 ui_action 對 e3 做 focus（8 ms），再 set_value 寫入 "hello from ui_action 0.10.0" （15 ms）。
  5. 再拍一次快照確認：e3 的值是 "hello from ui_action 0.10.0"。
  6. 再讀一次滑鼠位置。

兩次讀到的是同一個點：(284, 88)。文字寫進去了，游標沒有動。

3. 實機測試抓到的問題：sheet 裡的按鈕

接著我們結束 TextEdit。還沒儲存的文件跳出了儲存用的 sheet，也就是從視窗標題列往下滑出來的那種對話框。對 sheet 上的「刪除」按鈕呼叫 ui_action press，失敗了：

stale ref: e63 has left its window; take a new ui_snapshot and use its refs

每次都重拍快照，連試三次都一樣。我們用一段唯讀的 Swift 探測程式查原因：sheet 裡的控制項被問到 AXWindow 時，回的是 nil，而不是別的視窗。0.10.0 的檢查以為只有選單項目才會沒有 AXWindow，所以拒絕了這個 ref。按鈕的 AXParent 是 sheet，sheet 的 AXWindow 才是那個視窗。

這件事開成了 issue #98（標籤 bug、p2），由 PR #99 修正：元素沒有 AXWindow，或它的 AXWindow 不在快照記錄的路徑上時，檢查改成沿著 AXParent 往上找最近的視窗、sheet、drawer 或 popover，而且只有這個容器在記錄的路徑上才接受。往上最多找 50 步，會檢查有沒有繞圈，也受同一個時間預算限制。行程或角色改變還是會先被拒絕，也不會猜替代的元素。

PR #99 新增 8 個測試，總數 264 個，0 個失敗，CI 通過。它的實機檢查是唯讀的：把新規則套到 TextEdit 真的儲存 sheet 上，sheet 裡 15 個控制項全部通過，包括「刪除」；用 0.10.0 的規則則一個也不通過。修正已經合併，會在 0.10.1 推出。在 sheet 裡真的按下按鈕這件事，目前由單元測試涵蓋，還沒有用 ui_action 在實機上重跑。

4. 兩個審查者，以及稽核紀錄的外洩

每一個變更都交給兩個獨立的 AI 審查者，用的是不同的模型。它們平行審查，兩邊都核准同一個 commit 才會合併。PR #96 審了五輪，最後再加一次確認。

第一輪就抓到一個真的問題：透過 switchboard 對密碼欄位 set_value 時，那個值會寫進 switchboard 的稽核紀錄。switchboard（openab-sb）在把工具呼叫轉給電腦之前，就先把參數寫進 audit.jsonl。所以就算 Mac 那端拒絕了這次呼叫，那一行紀錄也已經寫下去了。這只能在 openab-sb 修，PR #96 因此一直等到修正合併並部署之後才合併。

修正是 openab-sb 0.2.2（PR #16、issue #14）。它在稽核紀錄裡遮掉帶有祕密的參數，不管藏在多深的物件或陣列裡：ui_action 的 value、輸入的文字、名稱裡有 password、secret、token、credential 這類字眼的鍵，以及 env 和 headers 裡的每一個值。字串變成 <redacted:N chars>，其他型別變成 <redacted>。只有稽核紀錄裡那一份被遮，電腦收到的仍是原本的參數。自由格式的字串，例如 shell 指令、腳本內容或網址的查詢字串，不會被檢查。

我們用一個 canary 驗證：經過部署好的 switchboard 送出一次 exec 呼叫，在 env 的 API_TOKEN 放一個假的 token。這個 canary 在稽核檔案裡出現 0 次，那次呼叫的紀錄在 token 原本的位置寫的是 <redacted:31 chars>。後來實機測試 TextEdit 的 set_value，在紀錄裡也是 "value":"<redacted:27 chars>"，27 正好是 "hello from ui_action 0.10.0" 的長度。

0.10.0 的發布說明也提醒使用 switchboard 的人：透過 ui_action 傳任何敏感內容之前，先升級到 openab-sb 0.2.2，並考慮輪替舊版本寫下的稽核檔案。

限制與接下來

  • set_value 會把整個值換掉。有些 app 要等確認或焦點移開，才會真正套用。
  • 會打開 sheet 或選單的 press，app 可能比較晚才回應。這時結果會標成 unconfirmed：動作可能已經發生，請重拍快照確認，不要直接再按一次。
  • 拖曳和多步驟手勢還是用 mouse。沒有 accessibility 節點、自己繪製的內容，還是用 screenshot 加 mouse。
  • Linux：issue #67 已經關閉，因為 macOS 的部分做完了。Linux 上用 AT-SPI 實作 ui_snapshot 和 ui_action 先延後，列為 p3，記在 issue #102，等有 Linux 機器真的需要時再做。在那之前，Linux 上請用 screenshot、mouse 和 key。

想試試看：更新到 OpenAB Computer 0.10.0，給它「輔助使用」權限，再從使用 owner profile 的 agent 依序呼叫 ui_snapshot、ui_action，最後再 ui_snapshot 一次。有用 switchboard 的話，先把它升級到 openab-sb 0.2.2。上一篇：OpenAB Computer 開始支援 macOS 的 accessibility tree。
