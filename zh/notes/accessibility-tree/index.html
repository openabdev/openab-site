OpenAB Computer 開始支援 macOS 的 accessibility tree

2026-11-09 · OpenAB Computer 0.9.0

你有沒有想過：當你請 Agent 幫你用滑鼠點擊遠端電腦桌面上某個 app 裡的一顆按鈕時，Agent 到底是怎麼做到精準點擊的？

OpenAB Computer 0.9.0 新增了 ui_snapshot 這個 MCP 工具：讀取 Mac app 的 accessibility tree，以 JSON 回傳。agent 現在可以直接用文字看到視窗裡的按鈕、欄位和標籤，連同它們在螢幕上的位置，不必再從截圖裡猜。

Agent 要怎麼點到對的按鈕？

所謂 computer use，就是讓 agent 操作一台電腦：看畫面、移動滑鼠、點擊、打字。點下去不難，難的是點到對的東西。畫面上有一顆「儲存」按鈕，agent 得知道它在哪裡、是不是真的是按鈕、現在能不能按。

常見的做法大致有四種。

  1. 1. 看截圖，猜座標。agent 每一步截一張圖，模型從圖裡判斷按鈕位置、回傳 x、y，再移動滑鼠點下去，再截圖確認。

    優點：最通用，只要畫面看得到，什麼 app 都能操作，包括遊戲和自己畫的介面。

    缺點：每一步都要傳一張圖，token 成本高、速度慢；座標是猜的，按鈕小、解析度或縮放比例不同時常點偏；模型看到的是像素，分不清按鈕和長得像按鈕的圖片，也不知道按鈕是不是灰掉了；點擊要真的移動游標，agent 工作時你就不能用那台電腦。

    例子：Anthropic 的 computer use 工具就是這樣運作：Claude 拿到截圖，回傳 left_click 這類動作和以截圖像素為單位的 [x, y]，由你的程式去執行。它的文件也列出目標很小時，點擊落在對的區域卻沒點中的情況，建議用 zoom 動作放大檢查。OpenAI 的 computer use 工具建立在它的 Computer-Using Agent 模型（CUA）上，同樣看截圖，回傳帶 x、y 的滑鼠和鍵盤動作，截圖算作圖片輸入。OpenAI 另外也提供一種做法，讓模型寫程式（Playwright 或 PyAutoGUI）來操作介面。

  2. 2. 先在截圖上標號，再請模型選（常被稱為 set-of-mark）。先用另一個視覺模型偵測元件、框起來編號，再請 agent 回答「按 7 號」。

    優點：模型不用自己算座標，點偏少很多。

    缺點：還是每步要傳圖，又多一個偵測模型，漏掉或框錯，agent 就跟著錯，也不知道元件狀態（能不能按、目前的值）。

    例子：這個做法出自 Set-of-Mark 這篇論文：用現成的分割模型把圖切成區塊，疊上數字或框，模型看著標好的圖回答。Microsoft 的 OmniParser 把它用在螢幕截圖上：一個偵測模型找出可以互動的區域，一個描述模型說明每個元素的用途，把截圖轉成一份結構化的元素清單。

  3. 3. 用 app 自己的 API 或腳本。例如用 AppleScript 叫 Finder 開資料夾，或用指令列工具。

    優點：最精準，不需要畫面。

    缺點：每個 app 都不一樣，很多 app 沒有這種介面，agent 要先知道每個 app 怎麼用。

    例子：Apple 的 AppleScript 可以直接控制「可腳本化」的 Mac app 和部分 macOS 功能；不支援腳本的 app 就用不上。

  4. 4. 讀 accessibility tree。作業系統本來就為螢幕閱讀器準備了一套介面（macOS Accessibility API、Windows UI Automation、Linux AT-SPI；網頁也有瀏覽器的 accessibility tree），把按鈕、欄位、選單描述成一棵樹：角色、標籤、目前的值、能不能操作，以及在螢幕上的確切位置。

    優點：回傳的是文字，便宜又快；種類、名稱、狀態由系統直接給；位置是確切的；每個元件可以有 ref，之後可以「對這個 ref 按下去」，連游標都不用移動。

    缺點：要看 app 有沒有好好支援，自己畫的介面、canvas、遊戲在樹裡常是空的；需要開「輔助使用」權限；介面很複雜時樹很大，要限制深度和節點數；畫面一變，舊的 ref 就失效，要重新讀。

    例子：Vercel 的 Agent Desktop 走的就是這條路：讀桌面 app 的 accessibility tree，以 JSON 回傳，每個 agent 能操作的元素都有 ref；用 ref 執行動作時不移動游標，也不搶走焦點。它支援 macOS、Windows 和 Linux。

四種做法對照
做法每步成本準確度涵蓋範圍知道狀態（能不能按、目前的值）搶走游標需要權限
1. 看截圖，猜座標高：每步一張圖低：座標用猜的最廣：看得到就行✗ 不知道✓ 會要：截圖和操控輸入
2. 標號再選（set-of-mark）高：圖片加偵測模型中：看偵測準不準廣：偵測得到就行✗ 不知道✓ 會要：截圖和操控輸入
3. app 的 API 或腳本低：一個指令高窄：要 app 有支援看 app✗ 不會看情況（macOS：自動化）
4. accessibility tree低：一段文字高：位置是確切的中：標準介面；canvas、遊戲常是空的✓ 系統直接給✗ 用 ref 操作時不會*要：輔助使用

* 用 ref 操作、不移動游標的是 ui_action，還在 PR #96 開發中，尚未推出。目前 agent 透過 OpenAB Computer 還是用 mouse 點擊，游標會動。

為什麼我們選 accessibility tree

對 OpenAB Computer 這種「agent 在遠端」的情境，成本最高的就是一直來回傳截圖。accessibility tree 把每一步從「傳一張圖、猜一次座標」變成「讀一段文字、選一個 ref」，也解決了點不準，因為位置不是猜的。對大多數標準的 Mac app 來說已經夠用。但它不是萬能的，所以我們保留截圖，三種一起用：原生 app 用 ui_snapshot 讀 accessibility tree；網頁用 browser_snapshot 讀瀏覽器的 accessibility tree；樹裡看不到的（canvas、自己畫的介面）回到截圖加 mouse。

這項工作背後的研究

這次的工作，起點是我們在 Muse 上為社群發表的一份研究報告。報告比較了三個專案。OpenCode Browse 讓 agent 在你自己的電腦上，操作你已經登入的瀏覽器。Vercel Agent Desktop 讓 agent 透過 accessibility tree 操作桌面 app：它回傳結構化的 JSON，每個元素都有一個 ref，用 ref 執行動作時不移動游標，也不搶走焦點。OpenAB Computer 則是把一整台機器借給在別處的 agent。報告也指出，對這個遠端 agent 來說，主要的成本花在截圖迴圈上。

我們把 Agent Desktop 的長處帶了過來：把 accessibility tree 當成帶有 ref 的結構化資料來讀，不再從像素裡猜，並做成 OpenAB Computer 的 MCP 工具 ui_snapshot。現在遠端 agent 除了瀏覽器，也能用結構化的文字讀原生 app。

為什麼截圖迴圈不夠用

在這之前，agent 透過 OpenAB Computer 操作 Mac，走的是這樣的迴圈：截圖、猜按鈕在哪裡、用 mouse 點下去，再截一張圖確認。

社群使用者 ttmuse 在 issue #67 寫下了這個迴圈的代價。這位使用者每天把 OpenAB Computer 當成雲端 agent 的手，遠端操作家裡的 Mac。每一步都要花圖片 token，小目標常常點不到，agent 工作時，真正的游標也被搶走了。

這個 issue 原本在等一個真正需要它的人。這則留言說明了有人真的需要，於是我們調高了優先順序，先從 macOS 開始做。

從 Agent Desktop 學到的事

動手之前，我們仔細讀了 Vercel Labs 的 Agent Desktop：README、概念文件，還有 macOS 的程式碼。Agent Desktop 讀取桌面 app 的 accessibility tree，以 JSON 回傳，每個 agent 能操作的元素都配有一個 ref。其中三個想法影響了我們的規劃：前兩個已經做進 ui_snapshot，第三個要等第二階段。

  • 用結構化的文字取代圖片。模型讀的是角色、名稱和值，不用在像素裡找按鈕。
  • 每個元素一個 ref，來自某一次快照。Agent Desktop 的 ref 只屬於產生它的那次快照。畫面一變，過期或對不上的 ref 會直接被拒絕，不會用猜的，agent 重新拍一次快照就好。
  • 操作不靠游標（第二階段）。Agent Desktop 用 ref 執行的動作走 accessibility API，不移動游標，也不搶走焦點。

issue #67 當初也列過另一個做法：讓 OpenAB Computer 直接呼叫 Agent Desktop，好處是自己要維護的程式碼比較少，代價是多一個外部依賴，也得跟著它的更新節奏走。最後我們決定把 accessibility tree 做成 OpenAB Computer 自己的 MCP 工具之一，放進原本就提供 screenshot、mouse、 key 的那支 Swift 常駐程式（PR #93）。

ui_snapshot 回傳什麼

預設讀取最前面那個 app 目前的焦點視窗。用 app（bundle id 或 app 名稱）、 pid、window 和 all_windows 可以換成別的目標。

每個節點都帶有角色、標題、值、說明、是否啟用或取得焦點，以及一個 frame。frame 用的是和 screenshot、mouse 相同的顯示點座標，所以 agent 不用先看螢幕，就能對準節點點下去。每個節點也有一個 ref（e1、e2⋯⋯），在同一個快照 id 之內不會重複。

下面是在一台 M4 Mac mini 上對 Finder 拍的真實快照，當時沒有開任何 Finder 視窗，所以這個「視窗」就是桌面本身，裡面兩張圖是兩顆已掛載磁碟的圖示。工具會回傳一份給模型讀的文字版：

上限、逾時與隱私

一次快照有上限。預設最多往下 20 層或 300 個節點，整個呼叫給 3 秒；呼叫端可以調高到 50 層、 2,000 個節點和 10 秒。每次呼叫 accessibility API 之前，工具都會設定最多半秒的訊息逾時，所以一個已經沒有回應的 app 拖不住它。

碰到上限或時間用完時，agent 拿到的是目前已經讀到的部分，標上 truncated 或 timed_out，不會變成錯誤。很長的文字只讀前 200 個字元，大份文件不會被整份複製出來。

密碼欄位一律遮蔽。遇到安全文字欄位，工具根本不會去要它的值，也不會往裡面讀。其他欄位則不遮蔽。

這點很重要，因為這棵樹裡有截圖看不到的文字：捲到畫面外的列、收合起來的內容、其他視窗。所以 ui_snapshot 只開放給 owner profile，而且需要 macOS 的「輔助使用」權限，也就是 mouse 和 key 本來就在用的那一個。

哪種畫面用哪個工具

  • 原生 Mac app：ui_snapshot。
  • 網頁：browser_snapshot，從瀏覽器讀取頁面結構。
  • 自己繪製的內容，例如 canvas，沒有 accessibility tree：照舊用 screenshot 加 mouse。

和 Agent Desktop 一樣的地方，以及還不一樣的地方

一樣的：兩者都讀 macOS 的 accessibility API，回傳 JSON 而不是圖片；都替元素配上只在單次快照內有效的 ref，差別是我們替每個節點都配，Agent Desktop 只替 agent 能操作的元素配；讀不完時都回傳部分的樹，而不是直接失敗；兩者裡面都沒有模型，迴圈由呼叫它的 agent 自己跑。

目前不一樣的：

  • OpenAB Computer 只能讀。Agent Desktop 已經能用 ref 點擊、輸入、設定值、移動焦點，而且不動游標。用 OpenAB Computer 的 agent 還是得用 mouse 點座標，真正的游標還是會動。
  • ref。我們的 ref 只是單次快照裡的標籤，工具本身不保留狀態。Agent Desktop 會把每個 ref 對應到辨識元素用的資訊並存下來，動作之前先確認還是同一個元素。
  • 平台。OpenAB Computer 目前只在 macOS 上讀得到這棵樹，Agent Desktop 支援 macOS、Windows 和 Linux。
  • 形式。ui_snapshot 是遠端 MCP server 裡的一個工具，給另一台機器上的 agent 使用。Agent Desktop 則在本機以 CLI、C 函式庫或 stdio MCP server 的形式執行。

接下來（尚未推出）

第二階段是 ui_action(ref)：用 ref 按按鈕、設定欄位的值、移動焦點或打開選單，不移動游標。真正解決游標被搶走的，是這一段。它也會把目前樹裡沒有的選單列加進來。對密碼欄位設定值則會被拒絕。

macOS 之後，規劃中的是以 AT-SPI 為基礎的 Linux 版本。兩者都還沒有時程，issue #67 會繼續開著追蹤。

想試試看的話：更新到 OpenAB Computer 0.9.0，給它「輔助使用」權限，再從使用 owner profile 的 agent 呼叫 ui_snapshot。
