OpenAB Computer 0.10.0, 접근성 트리 조작 완전 지원: 실측 4.7배 빠르고 토큰 55% 절약

M4 Mac mini 한 대에서 같은 TextEdit 작업을 두 가지 방식으로 10번씩 돌린 결과입니다.

2026-11-10 · OpenAB Computer 0.10.0

지난 개발 노트에서는 ui_snapshot을 소개했습니다. 그것이 1단계(OpenAB Computer 0.9.0)로, 에이전트가 Mac 앱의 접근성 트리를 읽을 수는 있었지만 조작은 아직 못 했습니다. OpenAB Computer 0.10.0 릴리스와 함께 나온 ui_action은 이 트리를 직접 조작합니다. 스냅샷의 snapshot_id와 ref를 넘기면 press, set_value, focus, show_menu, confirm, cancel을 할 수 있고, 커서는 움직이지 않습니다.

그렇다면 트리를 읽고, 조작하고, 결과를 확인하는 전체 과정을 어떻게 시험할까요?

어떻게 시험하나

가짜 접근성 공급자를 쓴 단위 테스트

CI 기기에는 화면이 없어서 단위 테스트는 실제 앱을 건드리지 않습니다. 창, 버튼, 텍스트 입력란을 흉내 내는 가짜 접근성 공급자 위에서 돌며 ui_action의 규칙을 하나씩 확인합니다.

  • ref는 자기가 나온 스냅샷에서만 쓸 수 있습니다. 만료된 스냅샷, 캐시에서 밀려난 스냅샷, 없는 ref는 거부됩니다.
  • 스냅샷 뒤에 요소가 바뀌면(사라졌거나, 역할이 바뀌었거나, 다른 프로세스에 속하거나, 원래 창을 떠났으면) 그 ref는 오래된 것입니다. 도구는 거부하고 스냅샷을 새로 찍으라고 하며, 비슷한 요소를 대신 고르지 않습니다.
  • 요소가 지원하지 않는 동작은 아무것도 하기 전에 거부하고, 지원하는 동작 목록을 알려 줍니다.
  • 비밀번호 입력란의 값은 다시 읽지 않고, 로그에도 응답에도 남기지 않습니다.
  • 호출하는 쪽이 activate: true를 넘기지 않으면 앱을 앞으로 가져오지 않습니다.
  • ui_action은 owner 프로필만 호출할 수 있습니다.

PR #96에서 이런 테스트 52개를 추가했습니다. M4 Mac mini에서 전체 swift test는 테스트 256개를 실패 0개로 통과했고, PR의 CI 검사도 모두 통과했습니다.

M4 Mac mini 실기기 종단 간 시험

단위 테스트는 규칙이 맞는지를, 실기기 시험은 실제 앱에서 전체가 동작하는지를 확인합니다. 에이전트가 스위치보드를 거쳐 M4 Mac mini를 조작했습니다. 원격 에이전트가 쓰는 것과 같은 네트워크 경로입니다.

  1. 마우스 위치를 읽습니다.
  2. TextEdit을 열고 새 문서를 만듭니다.
  3. ui_snapshot을 호출해 트리에서 텍스트 영역(AXTextArea)과 그 ref를 찾습니다.
  4. 그 ref에 ui_action으로 focus하고, 이어서 set_value로 문장 하나를 넣습니다.
  5. ui_snapshot을 다시 호출해 텍스트 영역의 값이 그 문장인지 확인합니다.
  6. 마우스 위치를 다시 읽어 처음과 비교합니다.

두 번 읽은 위치는 같은 점이었습니다. 글자는 들어갔고 커서는 움직이지 않았습니다. 아래 성능 측정에서도 트리 경로를 10번 더 돌렸고, 매번 글자가 문서에 들어갔으며 포인터는 그대로였습니다.

또한 모든 변경은 서로 다른 모델로 도는 독립적인 AI 리뷰어 두 명이 보고, 둘 다 같은 커밋을 승인해야 병합합니다.

얼마나 빨라졌나

같은 작업을 두 가지 방식으로 10번씩 측정했습니다. 비어 있는 새 TextEdit 문서에 The quick brown fox jumps over the lazy dog.(44자)를 입력하고, 들어갔는지 확인하는 작업입니다.

  • A) 스크린샷 반복: screenshot → mouse로 텍스트 영역 클릭 → key로 입력 → screenshot으로 확인.
  • B) 트리 경로: ui_snapshot → ui_action focus → ui_action set_value → ui_snapshot으로 확인.

이 작업에서 B가 쓴 입력 토큰은 표준 모델에서 A보다 약 55% 적었고(1,435 대 3,165), 고해상도 모델에서는 약 74% 적었습니다(1,435 대 5,427). B는 0.36초, A는 1.70초 만에 끝나 B가 약 4.7배 빨랐고, 포인터도 한 번도 움직이지 않았습니다.

A의 시간은 대부분 키 44개 입력(877 ms)과, 스위치보드를 거쳐 돌아오는 약 500 KB짜리 스크린샷 두 장에 들어갑니다. B의 ui_action은 호출마다 처음부터 끝까지 약 67 ms였고, 대부분은 네트워크 왕복입니다.

토큰 계산 방법: 이미지는 Anthropic 비전 가이드의 공식을 썼습니다. 이미지를 모델 한도에 맞게 줄인 뒤 ⌈너비/28⌉ × ⌈높이/28⌉입니다. 표준 모델(긴 변 1,568 px까지)은 1920×1080 스크린샷을 1456×819로 줄여 약 1,560 토큰, 고해상도 모델(긴 변 2,576 px까지)은 줄이지 않아 약 2,691 토큰입니다. 텍스트는 약 4자를 1토큰으로 셌고, 토크나이저는 돌리지 않았습니다. 모델이 실제로 보는 내용만 셌고, 도구 정의와 모델 자신의 출력은 넣지 않았습니다.

조건: M4 Mac mini(16 GB, macOS 15.7), 1920×1080 디스플레이 한 대, OpenAB Computer 0.10.0. 에이전트는 tailnet 위의 HTTPS로 스위치보드에 연결하고 거기서 Mac mini로 이어지므로, 호출마다 이 왕복 비용이 듭니다. 방식마다 10번, A와 B를 번갈아 돌렸고 처음 워밍업 한 쌍은 버렸습니다. 네 번의 도구 호출 시간만 쟀습니다. A의 클릭 좌표는 알고 있는 창 위치에서 정했고, 실제 모델이라면 첫 스크린샷에서 읽어 내야 합니다. 이 수치는 기기 한 대, 작업 하나에서 나왔고, 모델이 스크린샷이나 스냅샷을 보고 생각하는 시간은 들어 있지 않습니다.
