OpenAB Computer 0.10.0의 ui_action을 어떻게 시험했나

2026-11-10 · OpenAB Computer 0.10.0

창의 접근성 트리를 읽을 수 있게 된 에이전트는 여러분의 마우스를 빼앗지 않고 그 창의 버튼을 어떻게 누를까요? 누른 뒤에는 마우스를 건드리지 않았다는 것을 어떻게 증명할까요?

OpenAB Computer 0.10.0에 ui_action이 추가됐습니다. 지난 개발 노트에서 소개한 ui_snapshot이 화면을 읽는다면, ui_action은 조작합니다. 스냅샷의 ref를 받아 접근성 API로 버튼을 누르거나 입력란을 채우고, 커서는 제자리에 둡니다. 이 노트에서는 무엇을 하는지, 그리고 어떻게 시험했는지를 다룹니다.

ui_action이 하는 일

호출 형태는 ui_action {snapshot_id, ref, action}입니다(PR #96). 동작은 press, set_value, focus, show_menu, confirm, cancel과 increment, decrement입니다. 각 동작은 접근성 액션 하나에 대응합니다. press는 요소에 AXPress를, set_value는 AXValue 설정이며 값 전체를 바꿉니다. 요소가 그 동작을 지원하지 않으면 도구는 아무것도 하기 전에 거부하고, 지원하는 동작 목록을 알려 줍니다.

권장하는 흐름은 세 단계입니다. ui_snapshot, 그 ref 중 하나에 ui_action, 마지막으로 다시 ui_snapshot을 찍어 결과를 확인합니다.

도구는 입력 이벤트를 합성하지 않고 포인터도 움직이지 않습니다. 소스 코드를 훑는 테스트가 이를 지킵니다. 기본적으로 앱을 앞으로 가져오지도, 창을 올리지도 않습니다. 백그라운드 앱의 메뉴를 열 때처럼 꼭 필요하면 호출하는 쪽이 activate: true를 명시합니다.

ref는 자기 스냅샷 안에서만 유효합니다

도구는 최근 스냅샷 네 개를 각각 5분 동안 보관합니다. 동작하기 전에 ref를 다시 확인합니다. 같은 프로세스인지, 역할과 하위 역할이 그대로인지, 처음 찾은 창 아래에 아직 있는지. 메뉴 항목이라면 메뉴 막대가 아직 응답하는지. 하나라도 어긋나면 답은 stale ref: … take a new ui_snapshot입니다. 비슷해 보이는 요소를 골라 대신 누르지 않습니다.

누가 쓸 수 있는지, 그리고 비밀번호 입력란

ui_action은 owner 프로필에서만 쓸 수 있고, mouse, key와 같은 등급입니다. macOS 손쉬운 사용 권한도 필요합니다. 비밀번호 입력란에 set_value를 할 때 값은 다시 읽히지 않고, 로그에도 응답에도 남지 않습니다. 어떤 입력란이든 입력한 값은 오류, 로그 줄, 응답 텍스트에 나오지 않습니다. 스위치보드를 거칠 때는 비밀번호 입력란에 대한 set_value가 기본적으로 거부되며, 그 컴퓨터의 관리자가 직접 켠 경우에만 허용됩니다.

어떻게 시험했나

1. 가짜 접근성 공급자를 쓴 단위 테스트

CI 기기에는 GUI가 없으므로 테스트는 실제 앱을 건드리지 않습니다. ui_snapshot에는 원래 가짜 접근성 공급자가 있었고, ui_action의 테스트도 그 위에서 돕니다. PR #96은 세 묶음에 테스트 52개를 추가했습니다. UIActionToolTests 40개, UISnapshotCacheTests 5개, UIActivateTests 7개입니다.

다루는 경우는 다음과 같습니다. 만료됐거나 밀려난 스냅샷. 없는 ref. 사라졌거나, 역할이 바뀌었거나, 다른 프로세스에 속하거나, 원래 창을 떠난 요소. 지원하지 않는 동작과 지원하는 동작 목록. 동작마다 뒤에서 호출되는 접근성 액션. 비밀번호 값이 응답과 모든 로그 줄에 없을 것. 스위치보드를 거치면 비밀번호 입력란이 기본적으로 거부될 것. activate의 기본값이 false일 것. 프로필 권한 구분.

M4 Mac mini에서 swift test는 테스트 256개를 실행했고 실패는 0개였습니다. PR의 CI 검사도 모두 통과했습니다.

병합 전에 실기기에서도 시도했지만, 그 테스트용 빌드에는 손쉬운 사용 권한이 없어서 ui_action은 권한 오류만 돌려줬고 TextEdit 단계는 돌지 못했습니다. 이 부분은 권한이 있는 릴리스 빌드를 기다렸습니다.

2. M4 Mac mini 실기기 시험, 스위치보드 경유

0.10.0 릴리스 뒤, 원격 에이전트가 스위치보드를 거쳐 M4 Mac mini를 조작했습니다. 한 단계가 MCP 도구 호출 한 번이고, 스위치보드의 감사 로그에 시각이 남았습니다.

  1. 마우스 위치 읽기(osascript로 짧은 JXA를 실행해 NSEvent.mouseLocation을 읽음).
  2. TextEdit을 열고 새 문서 만들기.
  3. TextEdit의 ui_snapshot, 96 ms. 텍스트 영역은 [e3] AXTextArea.
  4. ui_action으로 e3에 focus(8 ms), 이어서 set_value로 "hello from ui_action 0.10.0" 입력 (15 ms).
  5. 스냅샷을 다시 찍어 확인: e3의 값은 "hello from ui_action 0.10.0".
  6. 마우스 위치 다시 읽기.

두 번 읽은 값은 같은 점, (284, 88)이었습니다. 글자는 들어갔고 커서는 움직이지 않았습니다.

3. 실기기 시험이 잡아낸 것: 시트 안의 버튼

이어서 TextEdit을 종료하자, 저장하지 않은 문서 때문에 저장 시트가 떴습니다. 창의 제목 막대에서 아래로 내려오는 종류의 대화상자입니다. 시트의 "삭제" 버튼에 ui_action press를 보내자 실패했습니다.

stale ref: e63 has left its window; take a new ui_snapshot and use its refs

매번 스냅샷을 새로 찍어 세 번 시도했고 세 번 모두 같았습니다. 읽기 전용 Swift 프로브로 원인을 찾았습니다. 시트 안의 컨트롤에 AXWindow를 물으면 다른 창이 아니라 nil이 돌아옵니다. 0.10.0의 검사는 AXWindow가 없는 것은 메뉴 항목뿐이라고 보고 이 ref를 거부했습니다. 버튼의 AXParent는 시트이고, AXWindow가 그 창인 쪽은 시트입니다.

이것은 issue #98(라벨 bug, p2)이 됐고 PR #99에서 고쳤습니다. 요소에 AXWindow가 없거나 그것이 스냅샷에 기록된 경로에 없으면, 검사는 AXParent를 따라 가장 가까운 창, 시트, 드로어, 팝오버를 찾고, 그 컨테이너가 기록된 경로에 있을 때만 받아들입니다. 최대 50단계까지 올라가고, 순환을 검사하며, 같은 시간 예산 안에서 돕니다. 프로세스나 역할이 바뀐 경우는 여전히 먼저 거부되고, 대신할 요소를 짐작하지도 않습니다.

PR #99는 테스트 8개를 추가해 모두 264개, 실패 0개였고 CI도 통과했습니다. 실기기 확인은 읽기 전용이었습니다. TextEdit의 실제 저장 시트에 새 규칙을 적용하자 "삭제"를 포함한 시트 안 컨트롤 15개가 모두 통과했고, 0.10.0의 규칙으로는 하나도 통과하지 못했습니다. 수정은 병합됐고 0.10.1에 실립니다. 시트 안에서 실제로 버튼을 누르는 동작은 단위 테스트로 확인했으며, ui_action으로 실기기에서 다시 눌러 보는 일은 아직 하지 않았습니다.

4. 두 리뷰어, 그리고 감사 로그로 샌 값

모든 변경은 서로 다른 모델로 도는 독립적인 AI 리뷰어 두 명에게 갑니다. 둘은 동시에 리뷰하고, 둘 다 같은 커밋을 승인해야 병합합니다. PR #96은 다섯 차례 리뷰와 마지막 확인을 거쳤습니다.

첫 차례에서 실제 문제가 나왔습니다. 스위치보드를 거쳐 비밀번호 입력란에 set_value를 하면 그 값이 스위치보드의 감사 로그에 남았습니다. 스위치보드(openab-sb)는 도구 호출을 컴퓨터로 전달하기 전에 인자를 audit.jsonl에 씁니다. 그래서 Mac 쪽이 호출을 거부해도 로그 줄은 이미 쓰인 뒤였습니다. 고칠 수 있는 곳은 openab-sb뿐이라, PR #96은 수정이 병합되고 배포될 때까지 병합을 미뤘습니다.

수정은 openab-sb 0.2.2(PR #16, issue #14)입니다. 감사 로그 줄에서 비밀을 담은 인자를 객체나 배열의 어느 깊이에 있든 가립니다. 대상은 ui_action의 value, 입력한 텍스트, password, secret, token, credential 같은 말이 이름에 들어간 키, 그리고 env와 headers의 모든 값입니다. 문자열은 <redacted:N chars>로, 다른 타입은 <redacted>로 바뀝니다. 가리는 것은 감사용 사본뿐이고 컴퓨터는 진짜 인자를 받습니다. 셸 명령, 스크립트, URL의 쿼리 문자열 같은 자유 형식 문자열은 검사하지 않습니다.

canary로 확인했습니다. 배포된 스위치보드를 거쳐 exec를 한 번 호출하면서 env의 API_TOKEN에 가짜 토큰을 넣었습니다. 감사 파일에 canary는 0번 나왔고, 그 호출의 줄에는 토큰 자리에 <redacted:31 chars>가 있었습니다. 실기기 시험의 TextEdit set_value도 "value":"<redacted:27 chars>"로 기록됐는데, 27은 "hello from ui_action 0.10.0"의 길이입니다.

0.10.0 릴리스 노트도 스위치보드 운영자에게, ui_action으로 민감한 내용을 보내기 전에 openab-sb 0.2.2로 올리고 이전 버전이 쓴 감사 파일의 교체를 검토하라고 권합니다.

한계와 다음 단계

  • set_value는 값 전체를 바꿉니다. 확인하거나 포커스가 옮겨 가야 반영하는 앱도 있습니다.
  • 시트나 메뉴를 여는 press는 앱의 응답이 늦을 수 있습니다. 그러면 결과는 unconfirmed로 보고됩니다. 동작이 이미 일어났을 수 있으니 다시 누르지 말고 스냅샷을 새로 찍어 확인하세요.
  • 드래그와 여러 단계의 제스처는 여전히 mouse를 씁니다. 접근성 노드가 없는 직접 그린 내용은 여전히 screenshot과 mouse입니다.
  • Linux: macOS 부분이 끝나서 issue #67은 닫혔습니다. Linux에서 AT-SPI로 ui_snapshot과 ui_action을 지원하는 일은 p3로 issue #102에 미뤄 두었고, Linux 기기에서 필요해지면 시작합니다. 그때까지 Linux에서는 screenshot, mouse, key를 쓰세요.

써 보려면 OpenAB Computer 0.10.0으로 업데이트하고 손쉬운 사용 권한을 준 뒤, owner 프로필의 에이전트에서 ui_snapshot, ui_action, 다시 ui_snapshot 순서로 호출하세요. 스위치보드를 쓴다면 먼저 openab-sb 0.2.2로 올리세요. 지난 노트: OpenAB Computer가 이제 macOS 접근성 트리를 읽습니다.
