OpenAB Computer가 이제 macOS 접근성 트리를 읽습니다

2026-11-09 · OpenAB Computer 0.9.0

에이전트에게 원격 컴퓨터 데스크톱의 어떤 앱에 있는 버튼 하나를 마우스로 눌러 달라고 할 때, 에이전트가 실제로 어떻게 정확히 그 버튼을 누르는지 궁금했던 적이 있나요?

OpenAB Computer 0.9.0에 MCP 도구 ui_snapshot이 추가됐습니다. Mac 앱의 접근성 트리를 읽어 JSON으로 돌려줍니다. 이제 에이전트는 창 안의 버튼, 입력란, 레이블을 화면 위 위치와 함께 텍스트로 받습니다. 스크린샷을 보고 짐작할 필요가 없습니다.

에이전트는 어떻게 맞는 버튼을 누를까요?

computer use는 에이전트가 컴퓨터를 다루게 하는 것입니다. 화면을 보고, 마우스를 움직이고, 클릭하고, 타이핑합니다. 클릭 자체는 쉽습니다. 어려운 것은 맞는 대상을 클릭하는 일입니다. 화면에 "저장" 버튼이 있다면, 에이전트는 그것이 어디 있는지, 정말 버튼인지, 지금 누를 수 있는지를 알아야 합니다.

흔히 쓰는 방법은 크게 네 가지입니다.

  1. 1. 스크린샷을 보고 좌표를 짐작하기. 에이전트는 단계마다 스크린샷을 찍고, 모델이 이미지에서 버튼 위치를 판단해 x, y를 돌려줍니다. 마우스를 그 위치로 옮겨 클릭한 뒤, 다시 스크린샷을 찍어 확인합니다.

    장점: 가장 범용적입니다. 화면에 보이기만 하면 게임이나 직접 그린 UI를 포함해 어떤 앱이든 다룰 수 있습니다.

    단점: 단계마다 이미지를 한 장씩 보내므로 토큰 비용이 크고 느립니다. 좌표는 짐작이라서 버튼이 작거나 해상도, 배율이 다르면 자주 빗나갑니다. 모델이 보는 것은 픽셀이라 버튼과 버튼처럼 생긴 그림을 구분하지 못하고, 버튼이 비활성화되어 있는지도 모릅니다. 클릭하려면 실제 커서를 움직여야 하므로 에이전트가 일하는 동안 그 컴퓨터를 쓸 수 없습니다.

    예: Anthropic의 computer use 도구가 이렇게 동작합니다. Claude는 스크린샷을 받고 left_click 같은 동작을 스크린샷 픽셀 단위의 [x, y]와 함께 돌려주며, 그 동작은 사용자 쪽 코드가 실행합니다. 문서에는 대상이 아주 작으면 클릭이 맞는 영역에 떨어져도 대상을 놓칠 수 있다고 적혀 있고, zoom 동작으로 확대해 확인하라고 권합니다. OpenAI의 computer use 도구는 Computer-Using Agent 모델(CUA)을 바탕으로 하며, 마찬가지로 스크린샷을 보고 x, y가 담긴 마우스와 키보드 동작을 돌려줍니다. 스크린샷은 이미지 입력으로 계산됩니다. OpenAI는 모델이 코드(Playwright나 PyAutoGUI)를 써서 UI를 다루는 방식도 제공합니다.

  2. 2. 스크린샷에 먼저 번호를 붙이고 모델에게 고르게 하기(흔히 set-of-mark라고 부릅니다). 먼저 다른 비전 모델로 화면의 요소를 탐지해 테두리를 두르고 번호를 매깁니다. 그러면 에이전트는 "7번을 눌러"라고 답합니다.

    장점: 모델이 좌표를 직접 계산하지 않아도 되므로 빗나가는 일이 훨씬 줄어듭니다.

    단점: 여전히 단계마다 이미지를 보내고, 탐지 모델이 하나 더 붙습니다. 탐지가 요소를 놓치거나 테두리를 잘못 그리면 에이전트도 그대로 틀립니다. 누를 수 있는지, 현재 값이 무엇인지 같은 요소의 상태도 모릅니다.

    예: 이 방식은 Set-of-Mark 논문에서 나왔습니다. 기존 분할(segmentation) 모델로 이미지를 영역으로 나누고 숫자나 테두리를 겹친 뒤, 모델이 표시된 이미지를 보고 답하게 합니다. Microsoft의 OmniParser는 이를 스크린샷에 적용합니다. 탐지 모델이 조작할 수 있는 영역을 찾고, 설명 모델이 각 요소의 역할을 적어, 스크린샷을 구조화된 요소 목록으로 바꿉니다.

  3. 3. 앱 자체의 API나 스크립트 쓰기. 예를 들어 AppleScript로 Finder에게 폴더를 열게 하거나, 명령줄 도구를 씁니다.

    장점: 가장 정확하고 화면이 필요 없습니다.

    단점: 앱마다 방식이 다르고, 이런 인터페이스가 없는 앱도 많으며, 에이전트가 앱마다 쓰는 법을 먼저 알아야 합니다.

    예: Apple의 AppleScript는 스크립트를 지원하는 Mac 앱과 macOS 일부를 직접 제어합니다. 스크립트를 지원하지 않는 앱에는 쓸 수 없습니다.

  4. 4. 접근성 트리 읽기. 운영체제에는 원래 화면 낭독기를 위한 인터페이스가 있습니다. macOS의 Accessibility API, Windows의 UI Automation, Linux의 AT-SPI이고, 웹 페이지에는 브라우저의 접근성 트리가 있습니다. 버튼, 입력란, 메뉴를 역할, 레이블, 현재 값, 조작할 수 있는지, 화면 위 정확한 위치와 함께 하나의 트리로 나타냅니다.

    장점: 돌려받는 것이 텍스트라 저렴하고 빠릅니다. 종류, 이름, 상태를 시스템이 직접 알려 줍니다. 위치가 정확합니다. 요소마다 ref를 붙일 수 있어서 나중에 "이 ref를 눌러"라고 할 수 있고, 커서를 움직일 필요도 없습니다.

    단점: 앱이 얼마나 잘 지원하느냐에 달려 있습니다. 직접 그린 UI, canvas, 게임은 트리가 비어 있는 경우가 많습니다. 손쉬운 사용 권한이 필요합니다. UI가 복잡하면 트리가 커지므로 깊이와 노드 수를 제한해야 합니다. 화면이 바뀌면 이전 ref는 쓸 수 없게 되어 다시 읽어야 합니다.

    예: Vercel의 Agent Desktop이 이 방식을 씁니다. 데스크톱 앱의 접근성 트리를 읽어 JSON으로 돌려주고, 에이전트가 조작할 수 있는 요소마다 ref를 붙입니다. ref로 동작할 때는 포인터를 움직이지 않고 포커스도 가져가지 않습니다. macOS, Windows, Linux를 지원합니다.

접근성 트리를 고른 이유

OpenAB Computer처럼 에이전트가 멀리 있는 경우, 가장 비싼 부분은 스크린샷을 계속 주고받는 일입니다. 접근성 트리를 쓰면 한 단계가 "이미지 한 장 보내고 좌표 한 번 짐작하기"에서 "텍스트를 읽고 ref 하나 고르기"로 바뀝니다. 위치를 짐작하지 않으니 클릭이 빗나가는 문제도 해결됩니다. 대부분의 표준 Mac 앱에는 이것으로 충분합니다. 다만 모든 화면을 다룰 수는 없어서 스크린샷은 그대로 두고 세 가지를 함께 씁니다. 네이티브 앱은 ui_snapshot으로 접근성 트리를 읽고, 웹 페이지는 browser_snapshot으로 브라우저의 접근성 트리를 읽고, 트리에 보이지 않는 것(canvas, 직접 그린 UI)은 screenshot과 mouse로 돌아갑니다.

이 작업의 바탕이 된 리서치

이번 작업은 우리가 커뮤니티를 위해 Muse에 공개한 리서치 보고서에서 시작했습니다. 보고서는 세 프로젝트를 비교합니다. OpenCode Browse는 에이전트가 내 기기에서 로그인된 브라우저를 다루게 합니다. Vercel Agent Desktop은 에이전트가 접근성 트리를 통해 데스크톱 앱을 다루게 합니다. 구조화된 JSON을 돌려주고 요소마다 ref를 붙이며, ref로 동작할 때는 포인터를 움직이지 않고 포커스도 가져가지 않습니다. OpenAB Computer는 기기 한 대를 통째로 다른 곳의 에이전트에게 빌려줍니다. 보고서는 그 원격 에이전트에게 주된 비용이 스크린샷 루프라고 짚었습니다.

우리는 Agent Desktop의 장점을 가져왔습니다. 픽셀로 짐작하는 대신 접근성 트리를 ref가 붙은 구조화된 데이터로 읽는 방식입니다. 이것을 OpenAB Computer의 MCP 도구 ui_snapshot으로 만들었습니다. 이제 원격 에이전트는 브라우저뿐 아니라 네이티브 앱도 구조화된 텍스트로 읽을 수 있습니다.

스크린샷 루프로는 부족했던 이유

지금까지 OpenAB Computer로 Mac을 다루는 에이전트는 이렇게 움직였습니다. 스크린샷을 찍고, 버튼 위치를 짐작하고, mouse로 클릭하고, 다시 스크린샷을 찍어 확인합니다.

커뮤니티 사용자 ttmuse 님이 issue #67에 이 루프의 비용을 적어 주었습니다. 이 사용자는 OpenAB Computer를 매일, 집에 있는 Mac을 움직이는 클라우드 에이전트의 손으로 씁니다. 단계마다 이미지 토큰이 들고, 작은 대상은 빗나가고, 에이전트가 일하는 동안 실제 커서를 빼앗긴다는 내용이었습니다.

이 issue는 정말 필요로 하는 사람을 기다리고 있었습니다. 그 댓글로 실제로 필요한 사람이 있다는 것을 알게 되어 우선순위를 올리고 macOS부터 시작했습니다.

Agent Desktop에서 배운 것

코드를 쓰기 전에 Vercel Labs의 Agent Desktop을 꼼꼼히 읽었습니다. README, 개념 문서, 그리고 macOS 코드입니다. Agent Desktop은 데스크톱 앱의 접근성 트리를 읽어 JSON으로 돌려주고, 에이전트가 조작할 수 있는 요소마다 ref를 붙입니다. 그중 세 가지 생각이 우리 계획의 모양을 정했습니다. 앞의 두 가지는 ui_snapshot에 들어갔고, 세 번째는 0.10.0에서 ui_action으로 출시했습니다.

  • 이미지 대신 구조화된 텍스트. 모델은 역할, 이름, 값을 읽습니다. 픽셀 속에서 버튼을 찾지 않아도 됩니다.
  • 요소마다 하나의 ref, 한 번의 스냅샷에서. Agent Desktop의 ref는 그것을 만든 스냅샷에 속합니다. UI가 바뀌면 오래되었거나 모호한 ref는 짐작하지 않고 거부되고, 에이전트는 새 스냅샷을 찍습니다.
  • 포인터 없이 조작하기(2단계, 0.10.0에서 출시). Agent Desktop의 ref 동작은 접근성 API를 거치며 포인터를 움직이지 않고 포커스도 가져가지 않습니다.

issue #67에는 OpenAB Computer에서 Agent Desktop을 호출하는 방안도 있었습니다. 직접 관리할 코드는 줄지만 외부 의존성과 그 업데이트 주기를 떠안게 된다는 비교였습니다. 결국 접근성 트리를 OpenAB Computer 자체 MCP 도구 중 하나로 만들기로 했고, screenshot, mouse, key를 이미 제공하는 Swift 데몬에 넣었습니다(PR #93).

ui_snapshot이 돌려주는 것

기본으로는 맨 앞에 있는 앱의 포커스된 창을 읽습니다. app(bundle id나 앱 이름), pid, window, all_windows로 다른 대상을 고를 수 있습니다.

각 노드에는 역할, 제목, 값, 설명, 활성 여부와 포커스 여부, 그리고 frame이 들어 있습니다. frame은 screenshot, mouse와 같은 디스플레이 포인트 좌표를 쓰므로, 에이전트는 화면을 먼저 보지 않고도 노드를 겨냥해 클릭할 수 있습니다. 노드마다 ref(e1, e2, …)도 붙는데, 같은 스냅샷 ID 안에서는 겹치지 않습니다.

아래는 Apple 실리콘 Mac에서 Finder 창을 하나도 열지 않은 상태로 찍은 실제 스냅샷입니다. 이때 창은 데스크톱 자체이고, 그 안의 두 이미지는 마운트된 드라이브 두 개의 아이콘입니다. 도구는 모델이 읽을 텍스트 형식을 돌려줍니다.

ui_snapshot snap-54785c06 · Finder (com.apple.finder) · 4 nodes · 46 ms
[e1] AXScrollArea desc="desktop" (0,0 1920×1080) disabled
  [e2] AXGroup desc="desktop" (0,0 1920×1080)
    [e3] AXImage "Data" (1823,145 64×64)
    [e4] AXImage "Backup" (1823,33 64×64)

같은 트리의 JSON(발췌, 일부 필드는 생략):

{
  "snapshot_id": "snap-54785c06",
  "app": { "name": "Finder", "bundle_id": "com.apple.finder" },
  "node_count": 4,
  "truncated": false,
  "timed_out": false,
  "elapsed_ms": 46,
  "limits": { "max_depth": 20, "max_nodes": 300, "timeout_ms": 3000 },
  "windows": [
    { "ref": "e1", "role": "AXScrollArea", "description": "desktop",
      "enabled": false,
      "frame": { "x": 0, "y": 0, "width": 1920, "height": 1080 },
      "children": [
        { "ref": "e2", "role": "AXGroup", "description": "desktop",
          "children": [
            { "ref": "e3", "role": "AXImage", "role_description": "image",
              "title": "Data", "description": "Data", "display": 0,
              "frame": { "x": 1823, "y": 145, "width": 64, "height": 64 } }
          ] }
      ] }
  ]
}

이번 한 번의 실행에서는 노드 네 개를 46 ms에 읽었습니다. 드라이브 이름은 여기서 일반적인 이름으로 바꿨습니다. “Data” 드라이브를 열려면 에이전트는 e3 frame의 중심 (1855, 177)을 더블클릭하면 되고, 위치를 찾으려고 스크린샷을 찍을 필요가 없습니다.

한도, 타임아웃, 프라이버시

스냅샷에는 한도가 있습니다. 기본으로 깊이 20단계나 노드 300개에서 멈추고, 호출 전체에 3초를 줍니다. 호출하는 쪽은 50단계, 노드 2,000개, 10초까지 올릴 수 있습니다. 접근성 호출 전마다 최대 0.5초의 메시지 타임아웃을 걸기 때문에, 응답을 멈춘 앱이 도구를 붙잡아 둘 수 없습니다.

한도나 시간이 다 되면 에이전트는 그때까지 읽은 부분을 truncated나 timed_out 표시와 함께 받고, 오류는 나지 않습니다. 긴 텍스트는 앞의 200자만 읽으므로 큰 문서가 통째로 복사되지 않습니다.

비밀번호 입력란은 항상 가립니다. 보안 텍스트 필드에 대해서는 도구가 값을 아예 요청하지 않고 안쪽도 읽지 않습니다. 다른 입력란은 가리지 않습니다.

이 점이 중요한 이유는 트리에 스크린샷에 보이지 않는 텍스트도 들어 있기 때문입니다. 스크롤로 가려진 행, 접힌 내용, 다른 창. 그래서 ui_snapshot은 owner 프로필에서만 쓸 수 있고, macOS 손쉬운 사용(Accessibility) 권한이 필요합니다. mouse와 key가 이미 쓰는 바로 그 권한입니다.

어떤 화면에 어떤 도구를

  • 네이티브 Mac 앱: ui_snapshot.
  • 웹 페이지: browser_snapshot. 브라우저에서 페이지 구조를 읽습니다.
  • canvas처럼 직접 그린, 접근성 트리가 없는 내용: 예전처럼 screenshot과 mouse.

Agent Desktop과 같은 점, 아직 다른 점

같은 점: 둘 다 macOS 접근성 API를 읽고 이미지 대신 JSON을 돌려줍니다. 둘 다 요소에 한 번의 스냅샷 안에서만 유효한 ref를 붙입니다. 우리는 모든 노드에, Agent Desktop은 에이전트가 조작할 수 있는 요소에 붙입니다. 둘 다 다 읽지 못하면 실패하는 대신 일부 트리를 돌려줍니다. 둘 다 안에 모델이 없고, 루프는 호출하는 에이전트가 돌립니다.

지금 다른 점:

  • ref로 조작하기는 0.10.0부터입니다. 그전까지 OpenAB Computer는 읽기만 했습니다. Agent Desktop은 이미 ref로 클릭, 입력, 값 설정, 포커스 이동을 하고 포인터도 움직이지 않습니다. 0.10.0부터는 ui_action도 ref로 누르기, 값 설정, 포커스 이동을 커서를 움직이지 않고 합니다. 드래그, 제스처, 직접 그린 내용은 여전히 mouse를 쓰고, 이때는 실제 커서가 움직입니다.
  • ref. 0.10.0부터 도구는 최근 스냅샷 네 개를 5분 동안 보관합니다. 동작하기 전에 요소가 아직 있는지, 역할이 같은지, 같은 창 안에 있는지 확인하고, 오래된 ref는 대신할 요소를 짐작하지 않고 거부합니다. Agent Desktop은 ref마다 요소를 식별할 정보를 저장해 두고, 동작하기 전에 같은 요소인지 확인합니다.
  • 플랫폼. OpenAB Computer가 트리를 읽는 곳은 아직 macOS뿐입니다. Agent Desktop은 macOS, Windows, Linux를 지원합니다.
  • 형태. ui_snapshot은 원격 MCP 서버의 도구 하나로, 다른 기기의 에이전트가 씁니다. Agent Desktop은 로컬에서 CLI, C 라이브러리, 또는 stdio MCP 서버로 실행됩니다.

2단계 출시: 0.10.0의 ui_action

2단계는 ui_action이며 OpenAB Computer 0.10.0에서 출시했습니다. snapshot_id와 ref를 넘기면 접근성 API를 통해 버튼 누르기, 입력란 값 설정, 포커스 이동, 메뉴 열기, 확인, 취소, 값 올리기와 내리기를 커서를 움직이지 않고 합니다. 커서를 빼앗기는 문제를 끝내는 것이 이 부분입니다. ui_snapshot에 include_menu_bar를 주면 메뉴 막대 항목에도 ref가 붙습니다. 스위치보드를 거칠 때는 소유자가 직접 켜지 않는 한 비밀번호 입력란에 값을 설정하는 것이 거부됩니다.

Linux(AT-SPI)는 p3로 issue #102에 미뤄 두었고, Linux 기기에서 필요해지면 시작합니다. macOS 부분이 끝나서 #67은 닫혔습니다. ui_action을 어떻게 시험했고 스크린샷 반복보다 얼마나 빠른지는 다음 노트에 있습니다: OpenAB Computer 0.10.0의 ui_action을 어떻게 시험했나.

써 보려면 OpenAB Computer 0.10.0으로 업데이트하고 손쉬운 사용 권한을 준 뒤, owner 프로필의 에이전트에서 ui_snapshot을 호출하고 이어서 ui_action을 호출하세요.
