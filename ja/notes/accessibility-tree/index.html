OpenAB Computer が macOS のアクセシビリティツリーを読めるようになりました

2026-11-09 · OpenAB Computer 0.9.0

エージェントに「リモートのコンピューターのデスクトップで、あるアプリのこのボタンをクリックして」と頼んだとき、エージェントがどうやって狙いどおりに正確にクリックしているのか、考えたことはありますか。

OpenAB Computer 0.9.0 で、MCP ツール ui_snapshot が加わりました。Mac アプリのアクセシビリティツリーを読み、JSON で返します。エージェントは、ウィンドウの中のボタンや入力欄やラベルを、画面上の位置とあわせてテキストで受け取れます。スクリーンショットから読み解く必要はもうありません。

エージェントはどうやって正しいボタンを押すのか

computer use とは、エージェントにコンピューターを操作させることです。画面を見て、マウスを動かし、クリックし、文字を入力します。クリックすること自体は簡単です。難しいのは、正しいものをクリックすることです。画面に「保存」ボタンがあるなら、エージェントはそれがどこにあり、本当にボタンなのか、今押せる状態なのかを知る必要があります。

よく使われる方法は、おおまかに四つあります。

  1. 1. スクリーンショットを見て、座標を推測する。エージェントは一手ごとにスクリーンショットを撮り、モデルが画像からボタンの位置を判断して x と y を返します。マウスをそこへ動かしてクリックし、もう一度スクリーンショットで確かめます。

    長所：最も汎用的です。画面に映っていれば、ゲームや独自に描画された UI も含めて、どんなアプリでも操作できます。

    短所：一手ごとに画像を一枚送るので、トークンのコストが高く、時間もかかります。座標は推測なので、ボタンが小さいときや解像度、拡大率が違うときによく外れます。モデルが見ているのはピクセルなので、ボタンとボタンに似た画像の区別がつかず、ボタンがグレーアウトしているかどうかもわかりません。クリックには本物のカーソルを動かす必要があり、エージェントが動いている間、そのコンピューターは使えません。

    例：Anthropic の computer use ツールはこの方式です。Claude はスクリーンショットを受け取り、left_click などの操作を、スクリーンショットのピクセル単位の [x, y] とともに返し、それを実行するのは利用者側のコードです。ドキュメントには、対象がとても小さいとクリックが近くに落ちても外れることがあると書かれ、zoom で拡大して確かめる方法が勧められています。 OpenAI の computer use ツールは Computer-Using Agent というモデル（CUA）にもとづき、同じくスクリーンショットを見て、x と y 付きのマウスとキーボードの操作を返します。スクリーンショットは画像入力として数えられます。OpenAI は、モデルがコード（Playwright や PyAutoGUI）を書いて UI を操作する方式も用意しています。

  2. 2. スクリーンショットに番号を付けてから、モデルに選ばせる（set-of-mark とも呼ばれます）。 まず別の視覚モデルで画面上の要素を検出し、枠で囲んで番号を振ります。エージェントは「7 番を押す」と答えます。

    長所：モデルが自分で座標を計算しなくてよいので、外れることがずっと少なくなります。

    短所：やはり一手ごとに画像を送り、さらに検出モデルが一つ増えます。検出が漏れたり枠を間違えたりすれば、エージェントもそのまま間違えます。押せるか、今の値は何か、といった要素の状態もわかりません。

    例：この考え方は Set-of-Mark の論文から来ています。既存のセグメンテーションモデルで画像を領域に分け、番号や枠を重ね、印の付いた画像を見てモデルに答えさせるものです。 Microsoft の OmniParser はこれをスクリーンショットに使います。検出モデルが操作できる領域を見つけ、説明モデルが各要素の役割を書き、スクリーンショットを構造化された要素の一覧に変えます。

  3. 3. アプリ自身の API やスクリプトを使う。たとえば AppleScript で Finder にフォルダを開かせたり、コマンドラインツールを使ったりします。

    長所：最も正確で、画面がいりません。

    短所：アプリごとにやり方が違い、こうした仕組みを持たないアプリも多く、エージェントはアプリごとに使い方を先に知っておく必要があります。

    例：Apple の AppleScript は、スクリプトに対応した Mac アプリと macOS の一部を直接操作できます。スクリプトに対応していないアプリには使えません。

  4. 4. アクセシビリティツリーを読む。OS には、もともとスクリーンリーダーのための仕組みがあります。macOS の Accessibility API、Windows の UI Automation、Linux の AT-SPI で、Web ページにもブラウザーのアクセシビリティツリーがあります。ボタン、入力欄、メニューを、ロール、ラベル、今の値、操作できるかどうか、画面上の正確な位置とともに、一本のツリーとして表します。

    長所：返ってくるのはテキストなので、安くて速いです。種類、名前、状態はシステムが直接教えてくれます。位置は正確です。要素ごとに ref を付けられ、あとで「この ref を押す」と指示でき、カーソルを動かす必要すらありません。

    短所：アプリがきちんと対応しているかどうかに左右されます。独自に描画された UI、canvas、ゲームは、ツリーが空のことがよくあります。「アクセシビリティ」の権限が必要です。UI が複雑だとツリーが大きくなるので、深さとノード数に上限が要ります。画面が変われば古い ref は使えなくなり、読み直す必要があります。

    例：Vercel の Agent Desktop はこの方法をとっています。デスクトップアプリのアクセシビリティツリーを読んで JSON で返し、エージェントが操作できる要素ごとに ref を付けます。ref による操作ではポインターを動かさず、フォーカスも奪いません。macOS、Windows、 Linux に対応しています。

四つの方法の比較

アクセシビリティツリーを選んだ理由

OpenAB Computer のようにエージェントが遠くにいる場合、いちばんコストがかかるのは、スクリーンショットを何度も行き来させることです。アクセシビリティツリーを使うと、一手が「画像を一枚送って座標を一回推測する」から「テキストを読んで ref を一つ選ぶ」に変わります。位置を推測しないので、クリックが外れる問題も解消します。標準的な Mac アプリの多くは、これで十分です。ただ、どんな画面にも使えるわけではないので、スクリーンショットは残し、三つを組み合わせています。ネイティブアプリは ui_snapshot でアクセシビリティツリーを読み、Web ページは browser_snapshot でブラウザーのアクセシビリティツリーを読み、ツリーに現れないもの（canvas や独自に描画された UI）は screenshot と mouse に戻ります。

この取り組みのもとになった調査

今回の取り組みは、私たちがコミュニティ向けに Muse で公開した調査レポートから始まりました。レポートは三つのプロジェクトを比べています。OpenCode Browse は、自分のマシンにあるログイン済みのブラウザーをエージェントに操作させます。Vercel Agent Desktop は、アクセシビリティツリーを通してエージェントにデスクトップアプリを操作させます。構造化された JSON を返して要素ごとに ref を付け、ref による操作ではポインターを動かさず、フォーカスも奪いません。OpenAB Computer は、マシン一台を丸ごと別の場所のエージェントに貸します。そのリモートのエージェントにとって、コストの大部分はスクリーンショットのループから生じている、というのがレポートの指摘です。

私たちは Agent Desktop の長所を取り入れました。ピクセルから推測するのではなく、アクセシビリティツリーを ref 付きの構造化データとして読むことです。これを OpenAB Computer の MCP ツール ui_snapshot にしました。リモートのエージェントは、ブラウザーだけでなくネイティブアプリも構造化されたテキストとして読めるようになりました。

スクリーンショットのループでは足りなかった理由

これまで、OpenAB Computer で Mac を操作するエージェントはこう動いていました。スクリーンショットを撮り、ボタンの位置を推測し、mouse でクリックし、もう一度スクリーンショットで確かめる。

コミュニティのユーザー ttmuse さんが、issue #67 でこのループのコストを書いてくれました。この方は OpenAB Computer を毎日、自宅の Mac を動かすクラウドのエージェントの手として使っています。一手ごとに画像のトークンがかかり、小さな対象は外れ、エージェントが動いている間は本物のカーソルを取られてしまう、というものです。

この issue は、本当に必要とする人を待っていました。このコメントで実際に必要な人がいるとわかったので、優先度を上げ、macOS から取りかかりました。

Agent Desktop から学んだこと

コードを書く前に、Vercel Labs の Agent Desktop をじっくり読みました。 README、コンセプトの文書、そして macOS のコードです。Agent Desktop はデスクトップアプリのアクセシビリティツリーを読んで JSON で返し、エージェントが操作できる要素ごとに ref を付けます。そのうち三つの考え方が私たちの計画を形づくりました。最初の二つは ui_snapshot に入り、三つ目は 0.10.0 で ui_action としてリリースしました。

  • 画像ではなく構造化されたテキスト。モデルが読むのはロール、名前、値です。ピクセルの中からボタンを探す必要はありません。
  • 要素ごとの ref は、一回のスナップショットのもの。Agent Desktop の ref は、それを作ったスナップショットに属します。UI が変われば、古い ref や曖昧な ref は推測せずに拒否され、エージェントは新しいスナップショットを撮ります。
  • ポインターを使わない操作（第 2 段階、0.10.0 でリリース）。Agent Desktop の ref による操作はアクセシビリティ API を通り、ポインターを動かさず、フォーカスも奪いません。

issue #67 では、OpenAB Computer から Agent Desktop を呼び出す案も挙げていました。自分で持つコードが減る一方で、外部への依存とその更新のペースを抱えることになる、という比較です。最終的に、アクセシビリティツリーを OpenAB Computer 自身の MCP ツールの一つにすることにし、 screenshot、mouse、key をすでに提供している Swift のデーモンに入れました（PR #93）。

ui_snapshot が返すもの

既定では、最前面のアプリのフォーカスされたウィンドウを読みます。app（bundle id かアプリ名）、pid、window、all_windows で別の対象を選べます。

各ノードには、ロール、タイトル、値、説明、有効かどうかとフォーカスの有無、そして frame が入ります。frame は screenshot や mouse と同じディスプレイのポイント座標なので、エージェントは画面を見なくてもノードを狙ってクリックできます。各ノードには ref （e1、e2…）も付き、同じスナップショット ID の中では重複しません。

以下は、Apple シリコンの Mac で Finder のウィンドウを一つも開いていないときに撮った、実際のスナップショットです。この場合のウィンドウはデスクトップそのもので、中の二つの画像はマウントされた二台のドライブのアイコンです。ツールはモデル向けのテキスト版を返します。

ui_snapshot snap-54785c06 · Finder (com.apple.finder) · 4 nodes · 46 ms
[e1] AXScrollArea desc="desktop" (0,0 1920×1080) disabled
  [e2] AXGroup desc="desktop" (0,0 1920×1080)
    [e3] AXImage "Data" (1823,145 64×64)
    [e4] AXImage "Backup" (1823,33 64×64)

この一回の実行では、四つのノードを 46 ms で読みました。ドライブ名はここでは一般的な名前に置き換えています。「Data」ドライブを開きたければ、エージェントは e3 の frame の中心 (1855, 177) をダブルクリックすればよく、場所を探すためのスクリーンショットはいりません。

上限、タイムアウト、プライバシー

スナップショットには上限があります。既定では深さ 20 階層か 300 ノードで止まり、呼び出し全体に 3 秒を割り当てます。呼び出し側は 50 階層、2,000 ノード、10 秒まで引き上げられます。アクセシビリティの呼び出しの前には毎回、最大 0.5 秒のメッセージタイムアウトを設定するので、応答しなくなったアプリに止められることはありません。

上限や時間に達したときは、それまでに読めた分を truncated か timed_out の印付きで返し、エラーにはしません。長いテキストは先頭 200 文字だけを読むので、大きな文書が丸ごとコピーされることはありません。

パスワード欄は必ずマスクします。セキュアテキストフィールドについては、ツールは値を一切問い合わせず、中も読みません。それ以外の入力欄はマスクしません。

これが大事なのは、ツリーにはスクリーンショットに写らないテキストも入っているからです。スクロールで隠れた行、折りたたまれた内容、ほかのウィンドウ。そのため ui_snapshot は owner プロファイルでしか使えず、macOS のアクセシビリティ権限が必要です。 mouse と key がすでに使っているのと同じ権限です。

どの画面にどのツールを使うか

  • ネイティブの Mac アプリ：ui_snapshot。
  • Web ページ：browser_snapshot。ブラウザーからページの構造を読みます。
  • canvas のように独自に描画された、アクセシビリティツリーのない内容：これまでどおり screenshot と mouse。

Agent Desktop と同じところ、まだ違うところ

同じところ：どちらも macOS のアクセシビリティ API を読み、画像ではなく JSON を返します。どちらも要素に、一回のスナップショットの中でだけ有効な ref を付けます。こちらはすべてのノードに、Agent Desktop はエージェントが操作できる要素に付けます。どちらも、読み切れないときは失敗せずに部分的なツリーを返します。どちらも中にモデルを持たず、ループは呼び出すエージェントが回します。

今のところ違うところ：

  • ref による操作は 0.10.0 からです。それまで OpenAB Computer は読むだけでした。 Agent Desktop は以前から、ref でクリック、入力、値の設定、フォーカスの移動ができ、ポインターも動かしません。0.10.0 からは ui_action も、ref で押す、値を設定する、フォーカスを移す操作をカーソルを動かさずに行います。ドラッグ、ジェスチャー、独自に描画された内容は今も mouse を使うので、その場合は本物のカーソルが動きます。
  • ref。0.10.0 から、ツールは直近四回のスナップショットを五分間保持します。操作の前に、要素がまだあり、ロールが同じで、同じウィンドウの中にあることを確かめ、古い ref は代わりを推測せずに拒否します。Agent Desktop は ref ごとに要素を特定するための情報を保存し、操作の前に同じ要素であることを確かめます。
  • プラットフォーム。OpenAB Computer がツリーを読めるのは今のところ macOS だけです。 Agent Desktop は macOS、Windows、Linux に対応しています。
  • 形。ui_snapshot はリモートの MCP サーバーにあるツールの一つで、別のマシンのエージェントが使います。Agent Desktop はローカルで、CLI、C ライブラリー、または stdio の MCP サーバーとして動きます。

第 2 段階をリリース：0.10.0 の ui_action

第 2 段階は ui_action で、OpenAB Computer 0.10.0 でリリースしました。 snapshot_id と ref を渡すと、アクセシビリティ API を通して、ボタンを押す、入力欄に値を設定する、フォーカスを移す、メニューを開く、確定する、キャンセルする、値を上げ下げする、といった操作をカーソルを動かさずに行います。カーソルを取られる問題を解消するのはこの部分です。 ui_snapshot に include_menu_bar を付ければ、メニューバーの項目にも ref が付きます。スイッチボード経由では、パスワード欄への値の設定は、所有者が有効にしない限り拒否されます。

Linux（AT-SPI）は p3 として issue #102 で後回しにし、Linux のマシンで必要になったら取りかかります。macOS の部分が終わったので #67 は閉じました。ui_action をどう試し、スクリーンショットの繰り返しと比べてどれだけ速いかは次のノートにあります： OpenAB Computer 0.10.0 の ui_action をどう試したか。

試すには、OpenAB Computer 0.10.0 に更新してアクセシビリティ権限を与え、 owner プロファイルのエージェントから ui_snapshot、続けて ui_action を呼んでください。
