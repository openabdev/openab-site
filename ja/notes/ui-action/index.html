OpenAB Computer 0.10.0 の ui_action をどう試したか

2026-11-10 · OpenAB Computer 0.10.0

ウィンドウのアクセシビリティツリーを読めるようになったエージェントは、あなたのマウスを奪わずに、どうやってそのウィンドウのボタンを押すのでしょうか。押したあと、マウスに触れていないことをどう証明すればいいのでしょうか。

OpenAB Computer 0.10.0 で ui_action が加わりました。前回の開発ノートで紹介した ui_snapshot は画面を読む道具で、ui_action は操作する道具です。スナップショットの ref を受け取り、アクセシビリティ API でボタンを押したり入力欄を埋めたりし、カーソルはその場に残ります。このノートでは、何ができるのかと、どう試したのかをまとめます。

ui_action でできること

呼び出しは ui_action {snapshot_id, ref, action} です（PR #96）。操作は press、set_value、focus、show_menu、confirm、cancel と、increment、decrement です。どれもアクセシビリティのアクションに対応していて、press は要素への AXPress、set_value は AXValue の設定で、値全体を置き換えます。要素がその操作に対応していなければ、ツールは何もする前に拒否し、対応している操作の一覧を返します。

想定している流れは三段階です。ui_snapshot、その ref の一つに ui_action、最後にもう一度 ui_snapshot で結果を確かめます。

ツールは入力イベントを合成せず、ポインターも動かしません。ソースを走査するテストがこれを見張っています。既定ではアプリを前面に出さず、ウィンドウも手前に出しません。バックグラウンドのアプリでメニューを開くときなど、必要な場合は呼び出し側が activate: true を明示します。

ref は自分のスナップショットの中でだけ有効

ツールは直近四回のスナップショットを、それぞれ五分間保持します。操作の前に ref をもう一度確かめます。同じプロセスか、ロールとサブロールが変わっていないか、見つけたときのウィンドウの下にまだあるか。メニュー項目なら、メニューバーがまだ応答するか。どれか一つでも外れれば、答えは stale ref: … take a new ui_snapshot です。似た要素を選んで代わりにすることはしません。

使える人と、パスワード欄

ui_action を使えるのは owner プロファイルだけで、mouse や key と同じ扱いです。macOS のアクセシビリティ権限も必要です。パスワード欄に set_value するとき、値は読み戻されず、ログにも応答にも出ません。どの欄でも、入力した値はエラー、ログの行、応答のテキストに出ません。スイッチボード経由では、パスワード欄への set_value は既定で拒否され、そのコンピューターの管理者が有効にした場合だけ通ります。

どう試したか

1. 偽のアクセシビリティ提供元を使った単体テスト

CI のマシンには GUI がないので、テストは本物のアプリに触れません。ui_snapshot にはもともと偽のアクセシビリティ提供元があり、ui_action のテストもその上で動きます。PR #96 では三つのスイートで 52 個のテストを加えました。UIActionToolTests が 40、UISnapshotCacheTests が 5、UIActivateTests が 7 です。

扱っているのは次のようなケースです。期限切れや押し出されたスナップショット。存在しない ref。消えた要素、ロールが変わった要素、別のプロセスの要素、元のウィンドウを離れた要素。対応していない操作と、対応している操作の一覧。各操作の裏で呼ばれるアクセシビリティのアクション。応答にもログのどの行にもパスワードの値が出ないこと。スイッチボード経由ではパスワード欄が既定で拒否されること。activate の既定が false であること。プロファイルの権限の区分。

M4 Mac mini で swift test は 256 個のテストを実行し、失敗は 0 でした。PR の CI チェックもすべて通りました。

マージの前に実機でも試しましたが、そのテスト用のビルドにはアクセシビリティ権限がなく、ui_action は権限がないというエラーを返すだけで、TextEdit の手順は動きませんでした。この部分は権限のあるリリース版を待ちました。

2. M4 Mac mini での実機テスト（スイッチボード経由）

0.10.0 のリリース後、リモートのエージェントからスイッチボード経由で M4 Mac mini を操作しました。一手ごとに MCP ツールを一回呼び、スイッチボードの監査ログに時刻が残っています。

  1. マウス位置を読む（osascript で短い JXA を動かし、NSEvent.mouseLocation を読む）。
  2. TextEdit を開き、新しい書類を作る。
  3. TextEdit の ui_snapshot、96 ms。テキスト領域は [e3] AXTextArea。
  4. ui_action で e3 に focus（8 ms）、続けて set_value で "hello from ui_action 0.10.0" を入れる（15 ms）。
  5. もう一度スナップショットを撮って確かめる。e3 の値は "hello from ui_action 0.10.0"。
  6. もう一度マウス位置を読む。

二回の読み取りは同じ点、(284, 88) でした。文字は入り、カーソルは動いていません。

3. 実機テストで見つかったこと：シートの中のボタン

続けて TextEdit を終了すると、保存していない書類のために保存用のシートが出ました。ウィンドウのタイトルバーから下りてくる種類のダイアログです。シートの「削除」ボタンに ui_action の press を送ると、失敗しました。

stale ref: e63 has left its window; take a new ui_snapshot and use its refs

毎回スナップショットを撮り直して三回試し、三回とも同じでした。読み取り専用の Swift のプローブで原因を調べました。シートの中のコントロールに AXWindow を尋ねると、別のウィンドウではなく nil が返ります。0.10.0 のチェックは「AXWindow がない」のはメニュー項目だけだと考えていたので、この ref を拒否しました。ボタンの AXParent はシートで、AXWindow がそのウィンドウなのはシートのほうです。

これは issue #98（ラベルは bug と p2）になり、PR #99 で直しました。要素に AXWindow がない場合や、それがスナップショットに記録された経路にない場合、チェックは AXParent をたどって最も近いウィンドウ、シート、ドロワー、ポップオーバーを探し、その入れ物が記録された経路にあるときだけ受け付けます。たどるのは最大 50 段で、循環を確かめ、同じ時間の予算の中で動きます。プロセスやロールの変化は今までどおり先に拒否され、代わりの要素を推測することもありません。

PR #99 ではテストを 8 個加えて合計 264 個、失敗は 0 で、CI も通りました。実機での確認は読み取り専用でした。TextEdit の本物の保存シートに新しい規則を当てると、「削除」を含むシート内の 15 個のコントロールがすべて通り、0.10.0 の規則では一つも通りませんでした。修正はマージ済みで、0.10.1 で出ます。シートの中で実際にボタンを押す動作は単体テストで確かめていて、ui_action による実機での押し直しはまだしていません。

4. 二人のレビュアーと、監査ログからの漏れ

すべての変更は、別々のモデルで動く二つの独立した AI レビュアーに渡します。二つは並行してレビューし、両方が同じコミットを承認したときだけマージします。PR #96 は五回のレビューと、最後の確認を経ました。

最初の回で本当の問題が見つかりました。スイッチボード経由でパスワード欄に set_value すると、その値がスイッチボードの監査ログに残っていたのです。スイッチボード（openab-sb）は、ツールの呼び出しをコンピューターへ転送する前に、引数を audit.jsonl に書きます。そのため Mac 側が呼び出しを拒否しても、ログの行はもう書かれていました。直せるのは openab-sb だけなので、PR #96 は修正がマージされ、デプロイされるまでマージを待ちました。

修正は openab-sb 0.2.2（PR #16、issue #14）です。監査ログの行で、秘密を含む引数を、オブジェクトや配列のどの深さにあっても伏せます。対象は ui_action の value、入力したテキスト、password、secret、token、credential のような語を名前に含むキー、そして env と headers のすべての値です。文字列は <redacted:N chars> に、それ以外の型は <redacted> になります。伏せるのは監査用の写しだけで、コンピューターには本当の引数が届きます。シェルのコマンド、スクリプト、URL のクエリ文字列のような自由形式の文字列は調べません。

canary で確かめました。デプロイ済みのスイッチボードを通して exec を一回呼び、env の API_TOKEN に偽のトークンを入れました。監査ファイルに canary は一度も出ず（0 回）、その呼び出しの行ではトークンの位置に <redacted:31 chars> がありました。実機テストでの TextEdit の set_value も "value":"<redacted:27 chars>" と記録され、27 は "hello from ui_action 0.10.0" の長さと同じです。

0.10.0 のリリースノートでも、スイッチボードを運用する人に、ui_action で機密を送る前に openab-sb 0.2.2 へ上げること、古い版が書いた監査ファイルの入れ替えを検討することを勧めています。

制限と、これから

  • set_value は値全体を置き換えます。確定するかフォーカスが移るまで反映しないアプリもあります。
  • シートやメニューを開く press には、アプリの返事が遅れることがあります。そのときの結果は unconfirmed と報告されます。操作は起きたかもしれないので、もう一度押さず、スナップショットを撮り直してください。
  • ドラッグや複数段のジェスチャーは今も mouse を使います。アクセシビリティのノードがない独自描画の内容は、今も screenshot と mouse です。
  • Linux：macOS の部分が終わったので issue #67 は閉じました。Linux で AT-SPI を使って ui_snapshot と ui_action を動かす作業は、p3 として issue #102 で後回しにしていて、Linux のマシンで必要になったら取りかかります。それまで Linux では screenshot、mouse、key を使ってください。

試すには、OpenAB Computer 0.10.0 に更新してアクセシビリティ権限を与え、owner プロファイルのエージェントから ui_snapshot、ui_action、もう一度 ui_snapshot の順に呼んでください。スイッチボードを使っているなら、先に openab-sb 0.2.2 に上げてください。前回のノート：OpenAB Computer が macOS のアクセシビリティツリーを読めるようになりました。
